# Text First C4 Architecture Formats

## Context

[[0026-mermaid-c4-diagrams-as-vault-content|ADR-0026]] made authored Mermaid C4
diagrams first-class vault content. [[0030-dot-for-generated-code-architecture|ADR-0030]]
kept generated Code architecture as Graphviz DOT because the exhaustive source
graph exceeded practical Mermaid rendering limits.

Future architecture viewers may live in Obsidian and VS Code, and may use
browser libraries, WASM helpers, canvas formats, or whiteboard-style editors.
Those viewers are useful for human review, but they must not become the
authoritative source of architecture truth.

The intended workflow is text-first: an LLM generates code or text architecture
artifacts, then a human reviews and validates those artifacts before relying on
them for implementation. Binary, opaque, or drawing-first artifacts make this
workflow harder to review, diff, validate, regenerate, and repair.

## Decision

All criv-supported C4 architecture formats must be code/text first.

The source artifact for every C4 diagram or generated architecture view must be
plain text or structured text that can be read in a diff, generated by an LLM,
reviewed by a human, and validated by `criv check`.

Supported source formats may include Markdown-fenced Mermaid, DOT,
Structurizr DSL/JSON, D2, JSON Canvas, Excalidraw JSON, or future text formats,
but criv must treat the text/JSON artifact as the source of truth. Rendered
images, browser canvases, editor state, and manually positioned visual views are
projections over that source, not authoritative architecture records.

criv must be able to output deterministic architecture artifacts for formats it
claims to generate. criv must also be able to verify the generated or authored
format without requiring the human viewer runtime. For each supported C4 format,
verification should parse or normalize the artifact into criv's C4 model before
running architecture checks such as duplicate aliases, unresolved relationships,
invalid C4 levels, missing labels, and stale `criv:source` references.

Editor viewers in Obsidian and future VS Code integrations may use WASM,
JavaScript rendering libraries, canvas APIs, or whiteboard libraries. These
viewers may improve layout, navigation, filtering, and review ergonomics, but
they must not replace CLI-owned generation and validation.

## Consequences

LLM-generated architecture stays easy to inspect before implementation. Humans
can review text diffs, run `criv check`, and reject invalid diagrams without
opening an editor extension or renderer.

Viewer-specific formats such as JSON Canvas and Excalidraw remain viable only if
their saved artifacts preserve enough structured text/JSON metadata for criv to
normalize and validate. If a viewer cannot round-trip C4 semantics through a
reviewable text artifact, it is not a criv architecture source format.

The CLI remains the authority for generated architecture freshness and
validation. Obsidian and VS Code viewers remain consumers of criv state and
artifacts, optionally sharing Rust logic through WASM.
